\title{Field-Level Financial Document Extraction with YOLO26 and Apache Spark: A Reproducible Pipeline, Its Failure Modes, and a Measured Evaluation}
\author{\IEEEauthorblockN{Ram Ghadiyaram}\IEEEauthorblockA{Independent Researcher\\Celina, TX, USA\\ram.ghadiyaram@gmail.com\\ORCID: 0009-0006-3730-0914}
\and\IEEEauthorblockN{Sashi Kiran Kaata}\IEEEauthorblockA{Independent Researcher\\Glendale, AZ, USA\\sashikiran9@gmail.com\\ORCID: 0009-0002-7980-2905}}
\maketitle
\begin{abstract}
Putting a vision model inside a Spark job looks routine and fails quietly. We build a field-level document extraction pipeline in which YOLO26 localizes fields and Tesseract reads each crop, executed with \texttt{mapInPandas} so the model loads once per partition. We catalog the integration defects that made a first version wrong, marking which we reproduced by running code, including a Spark image source that returns decoded pixels instead of file bytes and an Arrow failure on Spark 3.5 with JDK 21. On a synthetic form dataset with exact ground truth, a CPU-fine-tuned YOLO26n reaches \valNmsPrec\% detection precision and \valNmsRec\% recall, and \valNmsEndToEnd\% of text fields are read correctly end to end. Without class-wise suppression the end-to-end head emitted \valDefDup{} duplicate boxes and precision fell to \valDefPrec\%. Full-page Tesseract captured \valBaseCapture\% of the strings but does not say which field they belong to, so we do not claim an accuracy advantage. A \texttt{mapInPandas} job that loads the model once per partition was \valPatPartSixteenSpeedup{} times faster than a row-wise UDF that builds it on every call, on two CPU cores. A repeat on one GPU in a different host gave the same conclusions (\valGpuNmsEndToEnd\% end to end) and no inference speedup for the nano model. Data are synthetic, and no cluster, multi-GPU, or Textract measurements are reported. All numbers are generated from files in the released repository.
\end{abstract}
