\section{Results}\label{sec:results}
All numbers in this section are generated from the result files in the repository. The confidence threshold for each variant was chosen on the validation split by detection F1, and each variant was then scored once on the test split. After the final code changes we reran the evaluation protocol with the released code on the stored CPU model, and all scores, counts and chosen thresholds were identical to the files reported here, so the results are not from older code.

\subsection{Detection and end-to-end accuracy}
Table~\ref{tab:main} compares three operating points of the same fine-tuned model, which reaches a validation mAP50 of \valMapFifty{} and mAP50-95 of \valMapFiftyNinetyFive{}. Those headline scores say little about deployment behavior. At the default confidence of \valDefConf{}, the exported end-to-end head produced \valDefFields{} boxes for 300 true fields, and precision was only \valDefPrec\%. Of those, \valDefDup{} were duplicates of a field that already had a box, with a mean confidence of \valDefDupConf{} against \valDefTopConf{} for the box matched to each true field, and \valDefMissed{} fields had no box above the threshold. The NMS-free head is therefore not duplicate-free after a short nano fine-tune.

Three observations follow. First, adding class-wise suppression before OCR lifts precision from \valDefPrec\% to \valNmsPrec\% and end-to-end accuracy to \valNmsEndToEnd\%, and it also removes duplicate crops from the OCR stage. Second, tuning an NMS-free detector for validation F1 chose a high threshold (\valFreeConf{}) that traded away recall, and end-to-end accuracy fell to \valFreeEndToEnd\%, below the untuned default. F1 is not the end-to-end objective, and a threshold chosen for one can hurt the other. Third, the OCR stage is rarely the bottleneck. Among correctly localized text fields it was exact \valNmsOcrStage\% of the time with class NMS, and \valNmsOcrErrAllAccount{} \valNmsOcrErrCount{} errors were on account numbers: \valOcrErrExamples.

Fig.~\ref{fig:perclass} gives the per-class breakdown for the class-NMS variant. Account number is the weakest class, in both recall (\valRecAccountNumber\%) and OCR (\valOcrAccountNumber\%). Class-wise suppression removed same-class duplicates but not every extra box: \valNmsExtra{} extra boxes remained on the CPU run and \valGpuNmsExtra{} on the GPU run, and none overlaps a true field of its own class at IoU 0.5, so the duplicate count does not include them. The OCR step uses a plain crop with four pixels of padding, single-line mode, and no upscaling or thresholding. Several errors look like crop effects, such as a stray leading letter or a dropped final digit, and we did not ablate the crop handling.

\subsection{Comparison with full-page Tesseract}
Full-page Tesseract found \valBaseCapture\% of the 240 text strings somewhere on the page (95\% interval \valBaseLo{} to \valBaseHi), which is higher than the \valNmsEndToEnd\% end-to-end figure. We do not read this as a win for either side. On clean, large, printed text, page-level OCR reads almost every string, and our matching rule is lenient to it, because it never has to say which field a string belongs to. The detect-then-read pipeline pays for field attribution, which the baseline does not provide at all, and on this dataset it does not buy better reading. Whether detection helps on degraded scans, where page-level OCR loses accuracy \cite{thammarak2022,reisswig2019}, is the question this dataset cannot answer. Baseline cost was \valBaseSecPerDoc{} seconds per document on one process.

Detection and reading replicate: class-wise suppression again removed all same-class duplicates and gave \valGpuNmsEndToEnd\% end-to-end accuracy (95\% interval \valGpuNmsEndToEndLo{} to \valGpuNmsEndToEndHi), and without it the end-to-end head again emitted duplicates (\valGpuDefDup{} at confidence 0.25). The ordering of the three variants is the same on both devices. Differences of a few points between the two columns cannot be separated into device effects and training variance, because each column is one training run on a 60-document test set, and we did not test them for significance. The per-partition speedup over the row-wise pattern held (\valGpuPatPartSixteenSpeedup{} times), but the GPU did not make this job faster. Every pattern was slower in the GPU run than in the CPU run, for example \valGpuPatPartSixteenSec{} against \valPatPartSixteenSec{} seconds at batch 16, and the row-wise gap (\valGpuPatRowUdfSec{} against \valPatRowUdfSec{} seconds) is consistent with an extra CUDA initialization in every call. Host differences are a second possible cause, and we did not profile either. Training was the exception, and was much faster on the GPU. The GPU row therefore supports the same conclusions as the CPU run and shows no inference benefit for this small model.

Two earlier runs on the same GPU are worth recording. Both gave poor reading accuracy (\valFallbackEndToEnd\% end to end in the one we kept) because Colab lacked the DejaVu fonts, the generator silently used a different font, and the test images differed. The environment file recorded after the second run showed this, and the only change before the third run was installing the fonts, with no change to code or thresholds. The test split was therefore scored in three Colab runs, and we report the third because it is the first on the same images as the CPU run. Detection was unaffected (recall \valFallbackNmsRec\%), but reading was not. The released generator now stops with an error in that case. Reading accuracy on synthetic text is sensitive to the rendering environment, which is a further reason to treat all numbers here as properties of this dataset.

\section{Discussion and Limitations}
\textbf{What this supports.} The pipeline runs end to end under Spark, produces field-labeled text, and its CPU results can be regenerated from one repository. Loading the model per partition is faster than per row, and detection quality at a fixed threshold can differ sharply from the threshold-free mAP that training reports.

\textbf{What it does not support.} The dataset is synthetic, clean, and generated by one randomized form generator with three fonts and varied layout, noise and blur, so it is easy, and the high validation mAP reflects that. The results do not show that detection beats full-page OCR on real documents, and on this data it did not. There is one training run per device and a 60-document test split, so intervals are wide. The detector is the nano model. We ran the protocol on CPU and once on a single GPU in local Spark mode. Multi-node scaling, cluster start-up, cost, Spark GPU scheduling with the RAPIDS Accelerator, and Amazon Textract were not measured, and the cluster GPU configuration in the released code is untested. A regular expression over full-page OCR output could probably attribute these strongly formatted fields on this synthetic data, since account numbers, dates and amounts have fixed shapes, so the dataset gives no reason to prefer detection over such a rule. The test split was scored for three variants and, for the GPU, in more than one Colab run, although the threshold for each variant was chosen on validation only. The validation split also selected the checkpoint and gives the reported mAP. Stronger baselines, such as LayoutLMv3 \cite{huang2022layoutlmv3}, Donut \cite{kim2022donut}, and other open OCR engines, were not run.

\textbf{Cold start.} The batch design assumes cluster start-up cost is amortized over a queue of documents. It is a poor fit for sub-second interactive requests, for which a warm cluster or a dedicated model server is the better choice.

\textbf{Next steps.} The most informative next experiment is the same protocol on real, degraded scans with field-level labels, where the comparison with page-level OCR could go either way, followed by the GPU path on EMR with a larger model, where device use may matter more than it did here.

\section{Ethical Considerations}
Checks and identification documents contain sensitive personal data. All data here is synthetic. Any use of real documents should follow the institution\textquotesingle{}s data-governance process and data-minimization principles such as those in the GDPR \cite{gdpr}, with encryption at rest, separate access scopes for raw images and structured output, and human review for low-confidence detections rather than automated decisions. Synthetic data from one generator does not establish fair performance across banks, regions, and languages, and that should be tested directly.

\section{Conclusion}
We built and released a Spark pipeline that detects financial form fields with YOLO26 and reads each with Tesseract, and we checked it by running it. The integration defects were real and are cataloged. On clean synthetic forms the pipeline reaches \valNmsEndToEnd\% end-to-end field accuracy with class-wise suppression, the end-to-end head emitted duplicates without it, and full-page OCR read the same strings at least as well, without saying which field each belonged to. A \texttt{mapInPandas} job that loads the model once per partition was \valPatPartSixteenSpeedup{} times faster than a row-wise UDF on CPU, and \valGpuPatPartSixteenSpeedup{} times in a GPU run on a different host, where the nano model gained no inference speed. Real scanned documents, cluster-scale GPU execution, and stronger baselines are the open questions, and the released code is meant to make those experiments cheap to run.
